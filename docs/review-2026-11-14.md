# FinalFolio 全面审查报告

审查对象：`finalfolio-web`（容器 `16fe47dc1a40`，镜像 `deploy-finalfolio-web`），源码 `/opt/finalfolio/app`，线上入口 `https://finalfolio.com`（Caddy → Cloudflare）。
审查时间：2026-11-14。
审查方式：源码逐文件阅读 + 生产只读探测 + 在隔离副本（端口 3100、临时数据目录、本地 SMTP 接收端、同版本 Caddy 2.11.2 临时反代）做浏览器与接口实测。

---

## 一、总体结论

### 1.1 产品完成度

这是一个完成度相当高的产品：编辑器、账户中心、管理后台、公开翻书页、注册/登录/改密/条款、对象存储镜像、模板治理都有真实实现，且代码风格统一、TypeScript 严格模式通过、自带 `validate:mvp` 与 2 个 Playwright 用例可跑通。视觉语言高度统一（纸感米色、衬线标题、等宽小字标签），首屏文案与信息架构清晰。

### 1.2 但当前版本不具备上线条件

本次审查确认 **6 个阻塞级问题**，其中最严重的一个（编辑器选中带照片的页面后主线程 99% 占用、自动保存完全停摆）在线上生产构建中必然存在（生产 `dist` 与本地构建 md5 完全一致），属于“用户一正常使用就会遇到”的级别。另有 3 个静默数据丢失问题（保存竞态、多标签覆盖、访客本地图片被自身清理逻辑删除），都会让用户在不被提示的情况下丢内容。此外存在 1 个明文生产凭据、1 个路径遍历、多个依赖高危漏洞。

### 1.3 证据基线

- 生产 bundle 与源码一致：`dist/assets/EditorPage-DE9Z09T1.js`、`index-CcsmvpcT.js` 在服务器与本地构建中 md5 完全相同。
- 生产 `server/*.js` 与工作区 md5 全部一致，即线上运行的就是这份未提交代码。
- 类型检查 `tsc --noEmit` 通过；`vite build` 通过；`validate:mvp` 通过；自带 Playwright 2/2 通过（需改浏览器路径）。
- 自带测试没有覆盖本次发现的任何一个问题，说明“测试通过”不能作为上线依据。

### 1.4 版本与仓库状态

- `HEAD` 仍是 `68d1440 chore: update finalfolio favicon svg`（2026-04-06），工作区有 **144 个未提交变更**（约 1.9 万行新增），产品名仍从 `crazyalbum-*` 改名而来。
- 没有任何 CI 配置、没有 lint/format 配置，`package-lock.json` 的 264 条 `resolved` 全部指向 `http://mirrors.tencent.com`（明文 HTTP 第三方镜像）。

## 二、阻塞上线的问题（必须修复）

### B1【致命·性能/功能】编辑器选中“带照片的页面”后持续重渲染，主线程 99%、自动保存停摆

- **位置**：`src/components/MagazinePreview.tsx`（第 166 行 `getFallbackCrop` 每次返回新对象；第 255–262 行 `useEffect` 依赖 `onCropMetricsChange` 与 `dragMetrics` 并在 cleanup/正文中回写状态）配合 `src/routes/editor/useEditorUiState.ts`（第 198 行 `handleCropMetricsChange` 每次渲染重建）。
- **复现步骤**：
  1. 登录后在编辑器打开任意含照片的页面（例如第 4 页 triptych 放 3 张图）；
  2. 用 DevTools 观察主线程，或执行 `MutationObserver` 统计 DOM 变动；
  3. 观察 5 秒内保存请求（PUT）。
- **实际表现**（本地实测，数据来自 Playwright + CDP）：
  - 无照片页面：主线程占用 **0%**、DOM 变动 0；
  - 含 3 张照片页面：主线程占用 **99%**、每 500ms 约 **8,000–15,000 次 DOM 变动**，持续不停；
  - 5 秒内 **0 次自动保存请求**（自动保存的 1.2s 防抖被不断重置导致永远不触发）；
  - 点击“应用模板”后每 700ms 约 2.5 万次 DOM 变动，自动保存同样为 0。
- **期望表现**：页面空闲时无持续渲染，主线程占用接近 0，编辑后 1.2s 内触发一次保存。
- **影响**：编辑器在真实使用场景（页面有图）中卡顿、耗电、风扇狂转；自动保存永远不触发，用户只能手动点 Save，一旦关闭标签页即丢失；移动端会直接失去响应。
- **修复建议**：
  1. 让 `getFallbackCrop` 返回稳定对象（对同一 crop 做 memo，或在父层只传已规范化的 crop）；
  2. `handleCropMetricsChange` 用 `useCallback` 固定引用，或在 `MagazinePreview` 内用 ref 保存回调、effect 只依赖 `slot/asset/dragMetrics` 的稳定值；
  3. 把 `dragMetrics` 的比较改为数值比较（`maxOffsetX/maxOffsetY`），避免新对象触发 effect；
  4. 修完后用 React DevTools Profiler 确认无循环提交。
- **验收标准**：含 3 张照片的页面静置 10 秒，主线程占用 <5%，DOM 变动 <50；编辑标题后 2 秒内出现 1 次 PUT 且状态栏显示 Saved。

### B2【致命·数据丢失】访客“本地保存”的照片在上传后 16ms 被自身清理逻辑删除，刷新即丢失

- **位置**：`src/routes/editor/uploadOperations.ts`（第 460 行 `writePersistedDraftUpload` 写入 IndexedDB）+ `src/routes/editor/useEditorProjectLifecycle.ts`（第 160 行 `void syncPersistedDraftUploads(project)` 在项目状态尚未包含新资源时执行）+ `src/editor/storage.ts`（第 357 行 `syncPersistedDraftUploads`）。
- **复现步骤**：
  1. 未登录打开 `/editor`，选择一张本地图片上传；
  2. 页面提示 “1 photo added locally for this session.”；
  3. 在 DevTools → Application → IndexedDB → `finalfolio-draft-uploads-v1/uploads` 查看；
  4. 刷新页面或登录。
- **证据**（插桩记录，精确到毫秒）：
  ```
  48.143 put  guest-b64e38c3-… store=uploads
  48.159 delete guest-b64e38c3-… store=uploads   ← 16ms 后被删除
  ```
  刷新后文案：“Restored this local draft, but 1 cached photo could not be recovered and were removed.”，媒体库为空。
  已用对照实验排除环境因素：同一浏览器上下文中，不含 Blob 的 JSON 记录、含 Blob/File 的记录在刷新后均能保留。
- **期望表现**：访客选择“本地保存”后，图片在刷新/登录后仍可用于继续编辑或附加到账户。
- **影响**：访客模式的核心承诺（“本机草稿”）不成立；用户可能在上传多张照片、排版完成后才发现全部丢失。文案仍在引导用户“Sign in to attach them to your account”，属于文案与结果不一致。
- **修复建议**：`syncPersistedDraftUploads` 必须在项目状态提交后执行，并且清理集合要包含“刚刚写入但尚未进入 project 的 assetId”；更稳妥的做法是上传写入成功后显式登记 active id，而不是从 React 状态反推。
- **验收标准**：访客上传 3 张后刷新，3 张仍在媒体库且可正常排版；登录后 3 张成功转入账户（`/api/uploads` 出现 3 条记录）。

### B3【致命·数据丢失】保存进行中继续输入的内容被服务端旧副本覆盖，界面却显示 “Saved”

- **位置**：`src/routes/editor/projectPersistence.ts` 第 234–242 行 `applyServerProjectRecordState`（用服务端返回的 `project` 整体替换本地状态）；`src/routes/editor/useEditorProjectLifecycle.ts` 第 153–178 行自动保存 effect（`saveState === 'saving'` 时直接 return，不排队）。
- **复现步骤**（已脚本化复现）：
  1. 打开已保存项目，修改页面标题为 A；
  2. 用 DevTools 把 `PUT /api/projects/:id` 延迟 3 秒；
  3. 在请求飞行中继续输入 B；
  4. 等响应返回。
- **实际表现**：
  ```
  4.7s  PUT body: "Untitled Project ALPHA"
  5.6s  界面: "…ALPHA BRAVO"
  7.8s  响应返回 "…ALPHA"
  8.1s  界面: "…ALPHA"（BRAVO 消失），状态栏: "Saved 8:31 PM"
  服务端最终: "…ALPHA"（BRAVO 从未保存，也没有任何失败提示）
  ```
- **期望表现**：保存期间的新改动应排队并在本次保存后再次提交；回填时不得覆盖本地更新的内容；状态栏不得显示“已保存”而实际丢失。
- **影响**：在慢网络或大项目下极易触发，用户会以为内容已保存并关闭页面。
- **修复建议**：保存开始时快照 `revision`，响应回来后仅当本地 `revision` 未变化才回填；否则保留本地状态并立即排队下一次保存；状态栏区分 “Saved (with pending changes)”。
- **验收标准**：延迟 PUT 3 秒并在飞行中输入，最终服务端与界面均为 “ALPHA BRAVO”；无内容丢失，状态栏与磁盘一致。

### B4【严重·数据丢失】两个标签页同时编辑同一项目，后保存者静默覆盖前者

- **位置**：`PUT /api/projects/:projectId` 无版本号/If-Match 校验（`server/app.js` 第 2838–2860 行），前端也无冲突检测。
- **复现步骤**：同一项目在两个标签页打开 → A 改标题并等待保存 → B 改标题并等待保存。
- **实际表现**：服务端最终只有 B 的内容（`afterB: "…TAB-B"`，`aTextLost: true`），A 界面仍显示自己“已保存”的版本，没有任何冲突提示。
- **期望表现**：后保存者收到 409 冲突提示（“该项目已在其他窗口更新”），可选择覆盖或刷新。
- **影响**：多人协作/多设备场景下的静默数据丢失。
- **修复建议**：在项目记录中加入 `revision`（或使用 `updatedAt` 做乐观锁），PUT 携带 `If-Match`，冲突返回 409；前端提示并提供“用我的版本覆盖/重新加载”。
- **验收标准**：上述步骤中第二个保存请求返回 409，界面出现冲突提示，任一选择后两端内容一致。

### B5【严重·功能/文案】“Export PDF” 实际只是打开浏览器打印对话框，不生成 PDF 文件，也没有成功回执

- **位置**：`src/routes/editor/exportFlow.ts` 第 305–353 行（`window.print()`）；`src/editor/export.ts` 第 26 行文案 “Flatten the folio into a print-ready PDF…”。
- **复现步骤**：编辑器 → Export Center → 选择 PDF → 点击 “Export PDF”。
- **实际表现**：调用 `window.print()`（脚本计数为 1），状态提示 “Print dialog opened with 8 preflight warnings.”；导出事件只写入 `requested`，没有成功/失败回执（线上事件统计中 `export requested` 仅 1 条即为此原因）。
- **期望表现**：要么真正在浏览器端生成可下载的 PDF（如 pdf-lib/jsPDF），要么按钮与文案明确写成 “Print / Save as PDF via browser dialog”，并说明纸张尺寸、页边距由谁决定。
- **影响**：用户以为点了就会下载 PDF，实际得到系统打印对话框；不同浏览器结果不同（Safari/Firefox 的页边距与缩放差异大），PDF 质量不可控；运营侧无法统计导出成功率。这是“标识与实际行为不匹配”的典型。
- **修复建议**：短期改文案+引导（“将打开系统打印对话框，请选择‘另存为 PDF’”），并在打印后监听 `afterprint` 记录 `ok`；中期实现真正的客户端 PDF 生成。
- **验收标准**：按钮文案与实际结果一致；导出成功/失败事件可在管理后台统计；至少在一个主流浏览器中产出的 PDF 页面尺寸与设置一致。

### B6【严重·安全】生产 SMTP 凭据明文写入仓库配置，并可通过 `docker inspect` 读取

- **位置**：`deploy/docker-compose.yml` 第 9–14 行（`FINALFOLIO_SMTP_PASS: EH90wIT9` 等）。
- **证据**：`docker inspect finalfolio-web` 的 `Config.Env` 直接返回 `FINALFOLIO_SMTP_PASS=…`；该 compose 文件位于工作区（未提交但会随部署目录同步）。
- **影响**：任何能读取仓库、备份、CI 日志或宿主机 docker 元数据的人都能拿到 `noreply@finalfolio.com` 的发信密码，可冒充官方域名发钓鱼邮件。
- **修复建议**：改为 Docker secret / 环境变量注入（compose 里写 `${FINALFOLIO_SMTP_PASS}` 并在宿主机 `.env`（权限 600）或 secret 中提供）；立即轮换该密码；历史提交与备份中做清理。
- **验收标准**：仓库与 `docker inspect` 中不再出现明文密码；旧密码已失效；轮换后注册/找回密码邮件仍可送达。

## 三、确认问题清单（按严重程度与影响范围排序）

> 说明：以下均为**已确认**（有代码位置或实测证据）。推测项统一放在第五节。

### S1【严重·安全】登录接口没有任何频率限制/锁定

- 位置：`server/app.js` 第 2147–2162 行；`server/auth.js` 第 389–433 行。
- 证据：本地连续 25 次错误密码登录，全部返回 401，没有任何 429 或锁定；同 IP 的注册/重发验证/重置密码都有 5 次/小时限制，唯独登录没有。
- 影响：可被离线/在线撞库，配合已知邮箱可长期暴力尝试。
- 修复：按 IP + 账号双维度限流与指数退避，失败计数持久化；成功登录清零。
- 验收：同 IP 连续失败 10 次后返回 429 且带 `Retry-After`；账号维度同样生效。

### S2【严重·安全】会话 Cookie 缺少 `Secure`，且会话 ID 明文落盘、数据目录对其他本地用户可读

- 位置：`server/app.js` 第 273–275 行（`HttpOnly; SameSite=Lax`，无 `Secure`）；`server/auth.js` 第 513 行 `readSession(sessionId)` 直接用会话 ID 作为文件名；生产数据文件权限 `-rw-r--r--`。
- 证据：`/opt/finalfolio/app/data/sessions/*.json`、`users/*.json`、`tokens/*.json` 均为 644，宿主机任意本地用户可读；会话文件中直接保存会话 ID（即 Cookie 值），密码重置 token 也以明文保存。
- 影响：一旦宿主机有其他账户或备份泄漏，攻击者可直接复用会话/重置链接接管账户；`Secure` 缺失使 Cookie 可能经明文通道发送。
- 修复：Cookie 增加 `Secure`；会话表只存 token 哈希；token 同样哈希化；数据目录 700、文件 600；容器改用非 root 用户运行。
- 验收：响应头含 `Secure`；数据目录 `700`；磁盘上不存在可直接使用的会话/重置 token 明文。

### S3【严重·隐私】`/uploads/*` 永久公开且强缓存，删除项目/上传后图片仍可被任何人访问

- 位置：`server/app.js` 第 3706–3713 行（`express.static` + `immutable, maxAge: 30d`，无鉴权）。
- 证据：未登录 `GET /uploads/<任意存在文件>` 返回 200；删除项目只移除项目记录，资源文件保留在 `data/uploads`（设计上“保留资源”），URL 无签名、无过期。
- 影响：用户删除作品后，旧链接仍可被访问/传播；分享链接被撤销也无法撤回图片本身；符合“删除”预期但不符合实际行为。
- 修复：改为带签名/过期的资源 URL，或对 `/uploads` 加鉴权（公开分享页走短期签名）；删除项目时提供“同时删除未被引用图片”的选项；至少在隐私政策中明确说明。
- 验收：删除项目后其图片 URL 返回 403/404；公开分享页仍可正常显示。

### S4【严重·安全】项目相关路由存在路径遍历读取（未净化 `projectId`）

- 位置：`server/app.js` 第 2743 行（`POST /api/projects/:projectId/duplicate` 直接 `readProjectRecord(request.params.projectId)`），对比第 2776 行 GET 路由有 `sanitizeProjectId`。
- 证据：`POST /api/projects/..%2Fusers%2F<userId>/duplicate` 返回 `{"error":"Project payload is invalid."}`（说明文件已被读取并解析），不存在的路径返回 `Project not found.`，构成任意 JSON 文件的存在性/内容探测通道。
- 影响：已登录用户可探测/读取 `data/` 下其他 JSON 文件；结合其他缺陷可能放大。
- 修复：所有 `:projectId` 入口统一调用 `sanitizeProjectId`；`createProjectFilePath` 内部再做一次 basename 校验。
- 验收：上述请求返回 `Invalid project identifier.`；对 `..`、绝对路径、编码斜杠均拒绝。

### S5【严重·稳定性】编辑器在 Hook 之前提前 return；全站无 ErrorBoundary

- 位置：`src/routes/EditorPage.tsx` 第 454–456 行 `if (!selectedPage && loadState === 'ready') return null;`，其后的 `useEditorUiState`（第 476 行）等 Hook 才被调用；全仓库无 `componentDidCatch`/`getDerivedStateFromError`。
- 影响：一旦出现“无选中页”的边界状态，React 会抛 “Rendered fewer hooks than expected” 并卸载整棵树，用户看到白屏；任何一处渲染异常都会导致整站不可用且无兜底。
- 修复：把提前 return 移到所有 Hook 之后；增加全局 ErrorBoundary（含“重新加载”“返回编辑器”入口）与 `window.onerror/unhandledrejection` 兜底提示。
- 验收：强制构造无选中页状态不白屏；人为抛错时显示可恢复的错误页而非空白。

### S6【严重·可用性】“自动保存”在页面持续重渲染时永不触发，且状态文案会掩盖保存状态

- 位置：`useEditorProjectLifecycle.ts` 第 153–178 行（依赖 `saveProject`，该函数每次渲染重建，无 `useCallback`）；`EditorPage.tsx` 第 715 行 `statusText = … message ?? fallbackStatus`（操作消息会长期覆盖保存状态）。
- 证据：含照片页面连续 5 秒悬停模板卡片，PUT 次数为 **0**；停止悬停后才出现 1 次；应用模板后 12 秒仍无 PUT。状态栏此时显示的是上一条操作消息（如 “Preset applied…”），用户完全看不到“未保存”。
- 影响：用户以为已自动保存，实际没有；关闭页面即丢失。
- 修复：`saveProject` 用 `useCallback` 稳定引用（并确保依赖正确），或把防抖改为基于 `project` 快照的 `setTimeout` + ref；保存状态与操作消息分开展示（例如状态栏固定显示保存态）。
- 验收：持续重渲染 10 秒仍能按防抖节奏产生保存请求；状态栏在任何消息下都能看到当前保存状态。

### S7【严重·数据丢失】应用模板包（replace）与切换模板会丢弃内容，但提示文案声称“已保留”

- 位置：`src/routes/editor/pageOperations.ts` 第 149–188 行（replace 直接替换 `pages`）、第 190–199 行；`src/editor/demoData.ts` 第 940–983 行 `carryAssetsToTemplate`（目标槽位不足时直接丢弃多余图片，不提示）。
- 证据：

## 五、待验证项（推测，需进一步确认）

1. **iOS Safari 合并 JPG 的 canvas 上限**：`createCombinedJpeg` 按页累加高度，48 页 A4 在 print 质量下约 3.5 万像素高。Chromium 实测 60000px 仍可生成，但 Safari/iOS 有像素面积上限（约 1700 万像素），极可能失败。需真机验证并加页数/尺寸保护。
2. **生产备份是否真实存在**：文档提到 `/root/.openclaw/workspace/backup/scripts/run_project_backup.sh`，当前不可读，未见到 crontab/timer；若未运行，单目录文件存储（`/data`）无备份属于上线阻塞项。
3. **弱网下首页空白窗口**：本地（无网络延迟）首屏 FCP 约 0.67s、4 倍降速约 1.16s，未见明显白屏；但 `[data-reveal]` 初始 `opacity:0` 依赖 IntersectionObserver，弱网/低端机上可能出现 1–2 秒空白。
4. **`X-Forwarded-For` 伪造绕过限流**：应用层可绕过（轮换最左值全部 204）；经同版本 Caddy 临时反代实测**不可利用**（Caddy 覆盖 XFF，限流键落为真实 IP）。若未来应用被直接暴露（不经 Caddy）则会成立。
5. **`X-Forwarded-Host` 污染重置链接**：应用层可注入（实测重置链接变为 `https://evil.example/auth?reset=…`）；经 Caddy 实测被覆盖为真实 Host，线上不可利用。属于“纵深防御缺失”，建议 `PUBLIC_ORIGIN` 环境变量固化。
6. **邮件模板 XSS**：`actionLabel/actionUrl` 直接拼入 HTML；`actionUrl` 来自 Host/X-Forwarded-Host，`new URL()` 会拒绝含引号的 host，实际可利用性低，但缺少转义。
7. **“Asset path is invalid.” 的生产触发路径**：线上 928 条事件中有 25 条该项目保存失败；代码上 `saveProject({manual:false})` 不经过 `canSaveProject` 门禁，理论上会把 `blob:`/`guest-upload://` 发给服务端并得到 400；具体触发时机未完全复现（与 B2 同源风险）。
8. **超过 48 页/64 资源的上限提示**：客户端没有页数上限提示，服务端 `sanitizeProjectState` 会拒绝；用户可能在排到第 49 页保存时才发现。
9. **对象存储断开后的降级**：`hydrateStoredUploadAsset` 依赖 `readConfig()`，远程桶不可达时预览是否回退本地未做故障演练。
