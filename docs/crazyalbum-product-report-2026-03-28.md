# FinalFolio 产品现状与方向报告

日期：2026-03-28

## 1. 执行摘要

`FinalFolio` 已经不再只是一个“能摆几张图的 editor demo”，而是形成了可继续打磨的完整产品骨架：`homepage + auth + editor + admin + server-side persistence + mail + ops data`。

目前最有价值的判断不是“还能不能继续写功能”，而是：

- 产品主引擎已经成立，尤其是多页 issue 编排、图片裁切/缩放、项目保存、上传素材、打印/导出链路这条主流程已经具备持续迭代价值。
- 产品闭环已经开始成型，用户、项目、素材、会话、邮件验证、后台治理之间不再是松散的 demo 级拼接。
- 后续重点不该再是单点堆功能，而是把“创作体验”“治理能力”“产品转化”三条线继续拧紧，使三大表面职责清晰：
  - `homepage` 负责讲清产品与转化
  - `editor` 负责创作与输出
  - `admin` 负责治理与运营

一句话概括当前阶段：

> FinalFolio 已从“可演示的编辑器项目”迈到了“具备产品骨架、可以继续向真实经营推进”的阶段。

## 2. 当前完整能力盘点

### 2.1 Homepage

当前首页已经不只是静态海报页，而具备以下能力：

- 首页文案由服务端 `site content` 驱动，可在后台治理中更新，而不是完全硬编码在前端。
- 首页右侧 `Featured issue output` 使用与编辑器一致的 `MagazinePreview` 渲染器，可以展示真实 issue 输出，而不是单纯摆拍图。
- 可配置 featured issue，后台可以指定首页重点展示哪一个 live issue。
- 首页承担产品叙事职责，已经开始明确传达：
  - 这不是 endless gallery
  - 这是 photo issue / editorial issue 工具
  - 它强调页面节奏、可打印输出和叙事组织

### 2.2 Auth / 账号体系

当前已经具备最小可用但真实可跑通的账号系统：

- 用户注册
- 登录 / 登出
- 邮件验证
- 重发验证邮件
- 找回密码 / 重置密码
- 会话持久化
- 项目与用户绑定
- 上传素材与用户绑定
- 第一批管理员可由系统 bootstrap 或后台直接创建
- 后台可直接创建已激活、已验证的新用户

同时，邮件入口已具备最基本的防滥用能力：

- 注册页验证码，且由后端真实校验
- 注册接口按 IP 限流
- 验证邮件重发接口按 IP 限流
- 找回密码接口按 IP 限流
- 相关操作已接入基础事件记录，便于后续审计

邮件能力也已经收敛到统一 `mail service`，并从现有 SMTP 环境变量读取配置，而不是在各处散着写。

### 2.3 Editor / 创作主流程

编辑器已经是 FinalFolio 当前最成熟的主引擎，具备：

- 新建项目
- 本地草稿暂存
- 创建稳定项目 URL
- 已有项目加载 / 保存 / 更新 / 删除
- 多模板页面编排
- starter pack / template pack 起步
- 自定义布局
- 页面顺序组织
- 页面文案编辑
- 上传图片素材
- 图片 intrinsic size 读取
- fit / crop / scale 调整
- 预览页同步呈现
- 浏览器打印 / PDF 输出
- 模板治理接入，编辑器模板和 starter pack 不再完全写死在前端

这意味着它已经不是一个“单页海报编辑器”，而是一个以多页叙事 issue 为核心的创作系统。

### 2.4 预览 / 输出一致性基础

这是 FinalFolio 的核心竞争点之一，也是目前最值得继续守住的技术资产。

当前代码已经明确朝以下方向收敛：

- 使用共享的图片几何计算模块 `src/editor/imageGeometry.ts`
- `MagazinePreview` 被 homepage、editor、admin inspect 共同复用
- 预览测量逻辑优先使用未缩放的稳定尺寸，而不是被 transform 后的视觉尺寸
- 图片 fit / scale / offset 的计算不再完全依赖表面各自为政的 CSS 逻辑

这意味着：

- 首页 proof preview
- 编辑器预览
- 后台 inspect
- print / export

已经在向同一套页面模型靠拢，而不是继续分裂成三四套“看起来差不多、实际上漂移”的实现。

### 2.5 Admin / 治理后台

后台已经从早期“工程清单页”升级为可用的治理控制台，当前具备以下结构：

- `Overview`
- `Projects`
- `Uploads`
- `Governance`
- `Users`
- `Events`

具体能力如下。

#### Overview

- 总览用户数、项目数、上传数、导出数
- 存储占用概览
- 最近活跃与失败情况
- 错误类型拆分与近期活动信息

#### Projects

- 项目列表检索
- 查看 issue 标题、owner、更新时间等基础信息
- 项目健康信号，如 blank pages / missing assets / unused assets
- Inspect 预览第一页输出
- 管理员删除项目

#### Uploads

- 上传文件列表
- 预览素材
- 显示尺寸、体积、上传时间
- 显示 owner / 所属项目 / 引用页面 / slot
- 显示是否仍被项目引用
- 管理员仅在无引用时删除上传文件

#### Governance

- 模板启用/停用
- 模板排序、分类、标签
- starter pack 治理
- 首页文案治理
- featured issue 配置

这部分价值很高，因为它把原本埋在前端代码里的“产品运营层配置”逐步抬升到了后台。

#### Users

- 用户列表
- 搜索
- 用户状态管理
- 管理员直接创建用户

#### Events

- 最近事件
- 最近失败
- 按类型拆分的错误和操作数据
- 为后续审计、报警、后台诊断留出了空间

### 2.6 素材治理

当前素材治理已不再只有“上传”，而具备删除和一致性判断基础：

- 用户侧删除素材前会检查是否仍被项目引用
- 项目内删除素材前会检查该素材是否仍被页面 slot 使用
- 后台删除上传文件前会检查是否仍被任一项目引用
- 资产记录支持 `deletedAt`，形成可追踪的删除状态
- 文件删除与资产记录标记同时处理，避免“磁盘删了但元数据还活着”或“记录删了但文件还在”这类明显不一致

这套能力虽然还不算完整 DAM，但已经进入“可治理”的范围，而不是 demo 级堆文件。

## 3. 当前产品优势

### 3.1 叙事导向而非图库导向

很多同类产品强调“快速把图片贴上去”，FinalFolio 当前最鲜明的特点是：

- 用 issue 组织内容，而不是无限流
- 强调页面节奏，而不是单张图片最大化
- 天生适合摄影专题、品牌 lookbook、过程记录、作品集刊物

这使它的定位更接近轻量 editorial studio，而不是普通图库 SaaS。

### 3.2 预览与输出模型正在收敛

许多可视化编辑器最大的问题，是“编辑时一套，导出时一套”。FinalFolio 这轮已经在系统层面把几何模型往统一方向拉。

只要这条线继续守住，它会成为非常实在的产品优势：

- 用户更敢在浏览器里精修 crop / fit
- 输出预期更稳定
- 客服与返工成本更低

### 3.3 治理意识比多数早期编辑器项目更强

现在不少“编辑器产品”死在后面，是因为只有创作界面，没有治理界面。FinalFolio 已经提前把后台搭出来，并且开始接入：

- 用户
- 项目
- 上传素材
- 模板
- 首页内容
- 事件与失败

这意味着它更像在做产品，而不是只做一个炫技编辑器。

### 3.4 技术栈简单，迭代速度快

当前架构仍偏轻量：

- React + TypeScript + Vite
- Express 服务端
- 文件型持久化
- Docker Compose 部署

它的优点是：

- 容易看懂
- 易于直接改
- 适合快速推进功能和验证产品判断

在早期阶段，这种简单性是优势，不是缺点。

## 5. 当前短板与风险

### 5.1 数据层仍偏单机

当前数据持久化以文件记录为主，这对于现阶段非常高效，但后续若进入多人、多管理员、高频上传和更强审计场景，会碰到：

- 数据迁移成本
- 并发一致性
- 搜索和聚合能力不足
- 更细权限与审计的扩展成本

### 5.2 Admin 已可用，但还不算成熟后台

现在后台已经足够做治理基础，但距离真正成熟的产品后台仍有差距：

- 项目详情还不够深
- 用户治理仍较轻
- 模板生命周期还没有完整发布/归档概念
- site settings 还是偏“配置表单”，还不是完整运营 CMS

### 5.3 事件系统仍需要更可解释

当前事件记录已经建立，但失败归因还不够细。后续需要继续区分：

- 上传失败
- 认证失败
- 权限失败
- 资源缺失
- 导出失败
- 前端渲染异常

否则后台虽然“能看见失败”，但不一定“能快速定位失败”。

### 5.4 增长入口还不够强

首页已经比之前更像产品，但若要承担真正转化任务，仍需要继续增强：

- 真实案例展示
- 更强的 issue 证明
- onboarding 说服力
- 模板/starter pack 的结果预期
- 用户首次进入后的落地体验

## 6. 未来运营方向建议

这里不建议一上来做得很重，而是按“先能形成增长闭环，再慢慢运营化”的路径推进。

### 方向 A：把 homepage 做成真正的转化页

优先目标：

- 用真实 featured issue 展示成品质量
- 增加更可信的工作流证明
- 增加典型使用场景文案
- 强化 CTA 到注册/进入 editor 的承接

适合推进的动作：

- 做 3 组典型样例 issue
- 后台支持切换 featured issue
- 用不同主题场景验证首页叙事是否有效

### 方向 B：把模板体系做成产品资产

目前模板已经有治理基础，下一步最值得做的是：

- 建立官方模板集合
- 明确分类与使用场景
- 将热门 starter pack 做成 onboarding 入口
- 逐步形成“模板即产品能力”的运营资产

这会直接提升首用成功率。

### 方向 C：把 admin 从“运维视角”继续推向“产品运营视角”

建议下一阶段把后台逐步增强到：

- 项目详情页更完整
- 模板治理更像发布系统
- 上传治理支持更强筛选与清理策略
- site settings 继续扩大到 onboarding / empty states / marketing surfaces
- event/failure 继续往 audit log 方向走

### 方向 D：形成账号、配额、套餐的商业化基础

当前用户、项目、素材归属已经建立，后续很自然可以继续长出：

- 存储配额
- 项目数限制
- 导出次数策略
- 高级模板包
- 团队协作 / 多角色权限

也就是说，FinalFolio 已经具备往“可运营、可计费”方向演进的基础土壤。

## 7. 建议的下一阶段优先级

如果只选最值得继续打的方向，我建议是：

1. 继续提升 homepage 的说服力和首访转化。
2. 把 admin 的项目详情与模板治理进一步产品化。
3. 继续守住 preview / export 一致性，避免后面为了赶功能再次漂移。
4. 完善事件分类、失败诊断和审计信息。
5. 为后续配额、套餐和团队权限预留更明确的数据结构。

## 8. 结论

FinalFolio 当前最宝贵的不是“功能数量”，而是它已经具备了正确的产品骨架：

- 有前台表达
- 有创作主引擎
- 有账号归属
- 有后台治理
- 有邮件和安全防滥用基础
- 有共享预览/输出模型的方向

这使它不再停留在“编辑器能跑”的层面，而是已经进入“可以认真打磨成产品”的阶段。

只要接下来继续坚持三件事：

- 不把所有需求继续塞进 editor
- 不让 homepage 退回装饰页
- 不让 admin 停在工程列表页

FinalFolio 就有机会真正成长为一个面向照片叙事与轻量杂志编排的完整产品。
